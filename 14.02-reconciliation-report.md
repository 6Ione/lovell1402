# Afterglow 14.02 Reconciliation Report

Date: 2026-11-11  
Scope: static source inspection of the supplied Afterglow working archive, screenshot interpretation, binary-format/string inspection of `ps4debug.bin.bin`, and structural inspection of `OpenGoldHEN-main.zip`. No console execution was performed by this audit.

## Executive summary

The PHANTOMNET screenshots show a browser-side primitive reaching the Afterglow stage, but the captured attempt ends with **`exploit failed - please retry (reopen browser)`**. The log also reports `AG this kernel is already open` followed by `AG Not trying again`.

The matching Afterglow source contains an early-return guard that labels the kernel “already open” when a normal `mmap` request followed by `mprotect(PROT_READ|PROT_WRITE|PROT_EXEC)` succeeds. That test does not inspect kernel privilege, kernel patch state, or a kernel address. It tests whether the current process can create an RWX user mapping. Therefore, it is not a valid proof that a previous jailbreak succeeded and is a strong candidate explanation for the observed early abort.

A second source issue is that `jb-g.js` ignores the boolean returned by `runAfterglow()` and calls `finishUI(true)` unconditionally. In log mode `finishUI` is suppressed, but in normal mode this can present a false success state after an Afterglow failure.

The screenshot's `gadget-table-fits-module 15/15` is materially stronger evidence: `jb-g.js` reads bytes at 15 WebKit gadget offsets relative to the calculated WebKit base and counts exact signature matches. Assuming the screenshot corresponds to this source revision and the base calculation is correct, it is runtime evidence that those 15 signatures were present in the mapped WebKit image during that attempt. It does not validate every WebKit dependency, the LibcInternal gadget set, or the kernel stage.

## 1. Screenshot reconciliation

### Positive evidence

The screenshot captured at 19:40:49 shows:

- Browser reports firmware `14.02`.
- `PRIMITIVE-OK` is reported.
- Module bases are reported as aligned to `0x4000`.
- `gadget-table-fits-module` reports `15/15`.
- Afterglow reaches its own initialization and reports a CPU affinity pin.

These are program-reported observations. The 15/15 result is supported by a real byte-comparison loop in `jb-g.js` (the `GAD` table and `p.read1` checks), but it is not independent proof of the exploit chain.

### Negative / incomplete evidence

The same screenshot ends with:

`exploit failed - please retry (reopen browser)`

The Afterglow log immediately before it includes:

- `this kernel is already open -- a run has succeeded on this boot.`
- `Not firing again; reboot the console for a fresh one.`

This matches the early-return guard in `afterglow-g.js` around lines 1930–1937. It means the kernel exploit attempt appears to stop before the LibcInternal gadget validation and before the kernel trigger path.

### Important distinction: the table “PROOF-OK” checks

In `jb-g.js`, `OWN_KERNEL_STAGE` is true whenever the URL has the `afterglow` parameter. In that mode:

- `NEED_K` is set to an empty array.
- `needPatch` is set to an empty array.
- `needPl` is set to an empty array.

Consequently, `kernel-table-present`, `kpatch-table-present`, and `payload-table-present` can report success with empty `missing=[]` lists without validating the kernel offset table, the patch blob contents, or payload integrity. These checks only establish that the wrapper is intentionally delegating those jobs to Afterglow; they are not 14.02 compatibility proofs.

By contrast, `gadget-table-fits-module 15/15` is a real runtime byte check against the 15 entries in `GAD`.

## 2. Most likely observed early-abort path

`afterglow-g.js` performs the following before looking up `libSceLibcInternal.sprx`:

1. Seeds the required browser-libkernel syscall stubs.
2. Pins the thread to an allowed CPU core.
3. Calls `mmap(0, 0x4000, 3, 0x1002, -1, 0)`.
4. Calls `mprotect(mapped_address, 0x4000, 7)`.
5. If both calls succeed, prints “this kernel is already open” and returns `false`.

The mapping is created by the current process. `mprotect` changes the permissions of that process's mapping. This does not test whether kernel memory is writable, whether kernel patches are installed, whether the process has uid 0, or whether the kernel exploit previously succeeded. A normal process may be allowed to create an RW mapping and then request executable permission, subject to platform policy.

The comment claiming this is a success-only kernel-state check is therefore unsupported by the code. This is the leading source-level explanation for the screenshot's early stop. It is a hypothesis about the observed run, not a verified statement about the console's actual kernel state.

## 3. WebKit 14.02 compatibility evidence

`ps4_offsets.js` defines 14.00 by inheriting the 13.52 profile and clearing several old kernel-table/syscall-stub fields. 14.02 then inherits 14.00 and changes only its status string. That status string explicitly says:

- `webkit=assumed-13.52-identical`
- `kernel=afterglow-1402 (apm-UAF, offsets from 14.00 + shiftfit)`

The screenshot's 15/15 WebKit gadget check is useful runtime corroboration for the particular 15 signatures checked. It does not turn the whole 13.52 WebKit profile into a verified 14.02 profile. In particular, the check does not prove that `Math.expm1` base derivation, JS object-layout assumptions, import-slot derivation, every required gadget, or the browser primitive's reliability are correct across runs.

The Afterglow kernel stage has a separate `GADGETS` table for `libSceLibcInternal.sprx`. Those 14 signatures are checked later in `afterglow-g.js`, after the early-return guard. The screenshot therefore does not establish that any of the 14 LibcInternal signatures were checked during this attempt.

## 4. `ps4debug.bin.bin` inspection

File facts:

- Size: 3,178,344 bytes.
- SHA-256: `8bfe0507972718e6078778c5f9c44d84293197c0547239ab4227bdb351299b3e`.
- The file begins with an x86-64 relative jump, not an ELF header, PE/MZ header, or standard Mach-O header.
- An embedded ELF64 shared object begins at file offset `0x5c00`.
- Embedded ELF: `ET_DYN`, x86-64, entry point `0x120`, three program headers, 73 section headers.
- Embedded ELF contains named kernel-map sections including `.data.sysents`, `.data.allproc`, `.data.rootvnode`, `.data.prison0`, and `.data.kernel_map`.
- Printable strings identify `ps4debug-NG v1.3.4` / `PS4Debug-NG by Pharaoh2k v1.3.4`.
- Strings include both 14.00 and 14.02 patch-mismatch / occupied-syscall diagnostics, plus an `unsupported firmware` path.
- Strings also reference `libkernel.sprx`, `libkernel_web.sprx`, and `libkernel_sys.sprx`.

Interpretation:

This is a raw PS4Debug-NG payload/container with an embedded ELF component, not a decrypted WebKit or LibcInternal module. The 14.02 error strings show that the binary contains a 14.02-specific failure/reporting path; they do not prove that the 14.02 patch path succeeds. The embedded ELF's named `init_*sdk` sections include profiles through 13.52 and no visibly named 14.00/14.02 initializer. That is a reason to inspect its firmware dispatch and outer loader before treating it as a verified 14.02 debugger build.

## 5. OpenGoldHEN comparison

`OpenGoldHEN-main.zip` contains source/decompiled loader and kernel-payload components, plus firmware tables through 13.00 (including 13.00 tables). Its archive does not contain a 14.02 table. It is useful as a reference for loader structure, ELF mapping/relocation, kernel import resolution, and how firmware tables are organized. It is not a source of 14.02 offsets and should remain separate from Afterglow.

## 7. Next research tasks (static / non-destructive)

1. Treat the RWX user-mapping guard as a false-positive candidate and document a correct, independent kernel-state signal before any further exploit attempt. Do not infer kernel compromise from userland `mmap`/`mprotect` success.
2. Correct the wrapper's result handling so `runAfterglow()` returning `false` cannot be presented as success.
3. Reconcile the exact PHANTOMNET build/source revision with this working archive. The screenshot and source share diagnostic labels, but the final UI behavior suggests there may be a fork or wrapper difference.
4. Continue the LibcInternal audit only after confirming the execution path actually reaches `findLib()`; the current screenshot does not show that it does.
5. Inspect the embedded `ps4debug-NG` ELF's section dispatch and firmware selection logic. Treat the 14.02 diagnostic strings as error-path evidence, not proof of support.
6. Keep the OpenGoldHEN archive separate; do not import its firmware tables into Afterglow.

## Bottom line

The most actionable finding is not a missing SPRX file. It is the mismatch between the screenshot's early-abort log and Afterglow's own “kernel already open” guard. The guard tests a user-process RWX mapping, not kernel state. This likely prevents the attempt from reaching the LibcInternal and kernel stages. The 15/15 WebKit gadget check is useful positive evidence, while the table-presence diagnostics are largely vacuous in Afterglow mode.
